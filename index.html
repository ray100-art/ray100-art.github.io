01 · Flagship

ParkNairobi

Role
Sole engineer: backend, frontend and deployment
Stack
Java 21, Spring Boot 3, Spring Security, MySQL, Flyway, STOMP WebSocket, Leaflet, Docker, Nginx
Live demo ↗ API code ↗ Web code ↗

Problem

Drivers in Kenyan towns lose time circling for parking, and operators have no live picture of which bays are free. Most people pay with M-Pesa, so payment has to work on a phone, over an unreliable network.

What I built

  • A live map of bays across Nairobi and other towns, with nearest-bay search from the driver's location (Haversine distance), an occupancy heatmap, and turn-by-turn routes from OSRM.
  • Bookings that reserve a bay for 15 minutes, and sensor entry/exit events that keep each bay's status accurate.
  • Live updates: every status change is broadcast over STOMP WebSockets, so every open map changes at once without refreshing.
  • An admin console for occupancy, bookings and users.

Engineering decisions

  • Payments that settle once. Safaricom can deliver the same M-Pesa callback more than once. A payment only moves from PENDING, so a repeat is ignored, and the amount paid is checked against the booking's price before it is accepted.
  • An authenticated webhook. The callback has to be public, because Safaricom sends no token, so it is verified with a shared secret or Safaricom's IP ranges instead.
  • Access control in two layers: stateless JWT with DRIVER and ADMIN roles in the security filter chain, plus @PreAuthorize on admin operations. The WebSocket channel checks the token too.
  • A versioned schema: eight Flyway migrations own the database structure, so any environment can be rebuilt from scratch.
  • Protection from abuse: a request rate-limiting filter, CORS rules, and every credential read from the environment.

Delivery

Dockerfiles and docker-compose for the whole stack, with Nginx proxying /api and /ws. Unit tests cover the distance calculations and the slot service.

02 · AI & ML

DaktariAssist

Role
Sole engineer: prompt design, API and UI
Stack
Java 21, Spring Boot 3.3, Jackson, Groq API, Llama 3.3 70B, GitHub Actions
Code ↗

Problem

Clinicians in busy Kenyan facilities often work without a colleague to sanity-check a diagnosis. General AI chat tools answer in free text, ignore the local disease burden, and are hard to build on reliably.

How it works

case form→Spring Boot API→Llama 3.3 70B · Groq→parse → typed objects→report

Engineering decisions

  • Structured output, not chat. The system prompt fixes a strict JSON schema: a green, amber or red consistency rating, red flags, 2–3 differential diagnoses, 3–5 tests, and one follow-up question.
  • Reliable parsing. The service strips stray Markdown fences and parses the reply into typed Java objects. Failures come back as a structured error field instead of a crash.
  • Consistency: temperature 0.2, so similar cases get similar answers.
  • Local context and tone. The prompt covers malaria, typhoid, TB, HIV, brucellosis and meningitis, and phrases disagreement the way a supportive colleague would.

This is a decision-support prototype, not a medical device, and it has not been clinically validated. Clinical judgement stays with the clinician.

03 · E-commerce

DRIP Commerce

Role
Sole engineer: API and storefront
Stack
Java 17, Spring Boot 3.2, Spring Security, JJWT, JPA/Hibernate, MySQL, vanilla JS
API code ↗ Storefront code ↗

What I built

  • Accounts: passwords hashed with BCrypt, and a signed JWT on login that a request filter validates on every later call.
  • Catalogue and orders: full product CRUD, seeded on first start, and orders that move through pending → processing → shipped → delivered.
  • M-Pesa checkout: STK Push to the customer's phone, accepting 07…, 01…, +254… and 254… number formats, plus Safaricom's callback.
  • Storefront: search, wishlist, a cart that survives reloads, and an admin page.

Next steps

The repository lists its roadmap openly: lock management endpoints to admins, record payment status on the order from the callback, cache the Daraja token, and add integration tests. ParkNairobi's payment and access-control design is where these were carried further.
